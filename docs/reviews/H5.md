# H5: sync and sign-in

**Branch:** `h5-sync`, from `main` after PR #13 (the sign-in spike) · **SPEC:** v3.0 §12, §15 H5 · **App version:** 0.1.5 · **Date:** 2026-11-05

## What was built

H5 lets the family share one inventory: every phone works offline on its own copy and syncs with a server on Dan's Cloudflare free tier (§12). The spike (`docs/reviews/H5-spike.md`) settled sign-in: Cloudflare Access with emailed codes works in the home-screen app (question 1 passed). Questions 2 (a 30-day session) and 3 (an offline week) are still running; neither changes the design.

**Server (`worker/`, the Worker at `hiebert-home-inventory.dhiebert7251.workers.dev`):**
- `auth.ts`: the API checks Access's signed token (signature against the team's published keys, this app's audience, the issuer, expiry). It doesn't trust the plain email header.
- `store.ts`: every record of both parts in one D1 table (type, id, JSON, server time, person, deleted flag, sequence number). The tables are made on first use, so a new database needs no migration step.
  - **Pull** (`GET /api/sync?since=N`): everything with a sequence number above the phone's cursor, 500 at a time. A sequence number rather than a time, so two changes in the same millisecond can't be missed.
  - **Push** (`POST /api/push`): up to 50 changes, in order. Each is checked (the field rules the editors use, `src/domain/sync.ts`, plus links across parts), stored with the server's time and the person, and logged.
  - A person is made on first sign-in, named from the email ("dan.hiebert@…" → "Dan"); **Settings** changes it.
  - Daily at 09:00 UTC: deletes older than 90 days go, with their photo files (§12.2, D6), and activity older than 2 years (D8).
- `activity.ts`: the log lines (§3, F17), e.g. "moved Snowman lights to ATTIC-04 Christmas 4", "put out Garland on Mantel", "ticked “Water the tree” for Christmas", "finished setup of Christmas".
- `index.ts`: the routes, photo files in R2 (`PUT`/`GET /api/files/<photo id>`, `?thumb=1` for the thumbnail).
- `cloudflare.config.ts`: D1 `hiebert-home-inventory`, R2 `hiebert-home-inventory-files`, the Access team and audience tag, and the daily trigger. The first deploy creates the database and the bucket.

**Phone (`src/data/`, schema v6):**
- `outbox.ts`: a Dexie middleware records every change to a synced table, in the same transaction, as the record's new version or its delete. It keeps only the latest change per record, at the queue position of the first. None of the ~130 existing writes changed. New photos also go on an upload list.
- `sync.ts`: one sync is pull, push everything, pull again, then upload new photos and download others' thumbnails.
  - Writes that come from the server aren't sent back.
  - A record with a change waiting on this phone keeps the phone's version until that change is pushed.
- `db.ts` v6: new tables `outbox`, `uploads`, `syncMeta`, `people` and `activity`. Nothing already stored changes. A photo from another phone has no full image until it's opened.

**Screens:**
- **Every screen** (F15): a thin line under the top bar: "Synced 2 min ago", "Syncing…", "Offline · 3 changes waiting", "Signed out · 1 change waiting". Tapping it syncs now. Banners appear for:
  - a refused change: "Couldn’t save Broken: an item is in a bin or on a spot, not both. It’s back to the version on the server.";
  - a renumbered bin: "A-06 was taken by another phone, so your new bin is A-07. Reprint its label.";
  - **Sign in**, when the Access session has ended;
  - the first sync's choice (below).
- **First launch** (§12.5): when the server already has the family's data, a new phone downloads it ("Downloading the family’s inventory… 412 records") instead of the Set up step.
- **More › Activity** (F17): newest first, for the current part, with **Both parts** and filters by person, area and season. A change that replaced someone else's newer one says so: "Replaced Ann’s change from today 3:12 PM". **Item, bin and spot screens** show their last 10 entries.
- **More › Settings:** the sync state, **Sync now**, who you're signed in as, and **Your name**. The spike's sign-in check stays until questions 2 and 3 finish.
- **Backup & restore:** with sync on, Restore and Load sample data say they replace the data on every family phone, and the tick reads "I understand this replaces everything, on every family phone".

**Deploy:** GitHub Actions runs `npm run worker:deploy` on every push to `main` once the `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` secrets exist; until then that job is skipped. GitHub Pages keeps deploying the copy with no server, unchanged.

## Details I decided (for Dan to accept)

- **(a) A delete is removed from the phone at once**; only the server keeps the tombstone (§12.2). Screens didn't have to learn to hide deleted records.
- **(b) The pull cursor is a sequence number**, not a time (§12.1 says `since=<cursor>`).
- **(c) The server makes its own tables** on first use instead of a migration step, so a deploy is the whole setup.
- **(d) Who changed what is checked from Access's signed token**, not the email header Access also sends (defence in depth). The app's audience tag is in `cloudflare.config.ts`; it isn't a secret.
- **(e) One log line for a big push.** Over 10 lines in one push become one: "made 40 changes: 32 items, 8 bins" (a restore, a bulk move, the first upload). Changes to a list's order alone, a thumbnail, or the label-printed date get no line.
- **(f) Overwrites** are noted on the log line ("Replaced Ann’s change from 3:12 PM"), not in a banner (§12.1).
- **(g) Links left by another phone's delete are cleared** after a pull, as ordinary changes that sync: an item in a deleted bin gets no home yet; a deleted season or display is cleared; photos, tasks and runs of deleted records go. Otherwise a later backup wouldn't restore (§7 checks every link).
- **(h) A refused new record is removed from the phone**, since the server has no version to go back to. The banner names it. The server's id check is looser than the ids the app makes, so older records can't be refused for their id.
- **(i) First sync:**
  - an empty server gets this phone's records ("Upload mine" happens by itself);
  - a phone with only the starting lists (default categories and seasons, no areas, bins, items, displays, photos or runs) takes the server's quietly;
  - otherwise the banner asks, and **Back up, then use the server’s** saves a full backup first. "Upload mine" isn't offered then, as §12.1 says.
- **(j) Photos:**
  - a photo's thumbnail downloads with the sync;
  - its full image downloads when its carousel opens, and is kept;
  - a full backup fetches images this phone hasn't got, when online.
- **(k) Restore with sync on** goes to the server as ordinary changes: every record deleted, then the backup's records. A record another phone made and this phone hadn't pulled yet survives the restore. With sync every 2 minutes, that's unlikely.
- **(l) Your name** is changed in Settings, online only.
- **(m) When sync runs:** at launch, on returning to the app, every 2 minutes while open, on coming back online, and 1.5 s after a change (so a run of ticks goes as one push). Tapping the sync line syncs now.
- **(n) The GitHub Pages copy stays**, deploying as before with no server (its sync line is hidden, Activity says the log comes from the server). Retire it once everyone uses the workers.dev address.

## Before the first deploy (Dan)

1. **Turn on R2** in the Cloudflare dashboard (R2 Object Storage, then accept the free plan's terms). The API says "Please enable R2 through the Cloudflare Dashboard". The free tier is 10 GB.
2. **Deploy:** `! npm run worker:deploy` here. The first deploy creates the D1 database and the R2 bucket.
3. **Automatic deploys (optional):** create an API token (Workers Scripts, D1 and R2: Edit; Account Settings: Read) and add it with the account id as the repository secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. Until then, deploy with step 2.
4. **Family emails:** add each to the Access policy (HANDOFF §6).

## Phone check (after the first deploy)

1. On the GitHub Pages copy: More › Backup & restore › **Full backup**, saved to Files. The workers.dev copy has its own, separate storage.
2. Open the workers.dev address (signed in since the spike). More › App version shows **0.1.5**. The line under the top bar says "Synced …".
3. That copy has the spike's test data. Either keep it as the family's data (it uploads by itself, the server being empty), or first **Restore** the backup from step 1 there. The restore then goes to the server.
4. On a second device (Ann's phone, or Safari on a computer), sign in with another allowed email. It downloads everything.
5. Change an item on one phone; within about 2 minutes (or tap the sync line) it shows on the other. **More › Activity** shows it with the name.
6. Airplane mode: change something. The line says "Offline · 1 change waiting"; back online, it goes.
7. Take a photo on one phone; the other shows its thumbnail, then the full photo when opened.
8. Settings › **Your name**.
